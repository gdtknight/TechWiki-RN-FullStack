# 렌더링 첫걸음 09 - 버튼 하나를 누르면

> **이전**: [[렌더링 첫걸음 08 - 앱과 화면의 생명 주기|08 앱과 화면의 생명 주기]] · **다음(보충)**: [[렌더링 첫걸음 10 - 자식이 부모 함수를 부를 때|10 자식이 부모 함수를 부를 때]] · **목록**: [[렌더링 첫걸음 00 - 로드맵|로드맵]]

## 이 레슨에서 배우는 것

1. 웹에서 버튼 클릭 한 번이 **화면에 보이기까지** 거치는 모든 단계
2. 같은 일이 **React Native**에서는 어떻게 흘러가는지
3. 각 단계에서 **느려지는 원인**과 성능 체크리스트
4. 시리즈 전체를 한 장으로 정리

> 웹 예제는 React 19.3.1 + react-dom + jsdom에서 실행해 순서를 확인했습니다. jsdom에는 페인트가 없으므로 페인트 위치는 공식 문서를 근거로 씁니다. React Native 부분은 실행하지 않았습니다.

## 1. 이어달리기

### 비유로 이해하기: 이어달리기 경주

버튼을 누르면 바통이 여러 주자를 거쳐 결승선(화면)에 도착합니다.

| 주자 | 웹 | 배운 레슨 |
|---|---|---|
| 1 | 브라우저가 입력을 받아 이벤트를 만든다 | [[렌더링 첫걸음 02 - 프레임과 이벤트 루프\|02]] |
| 2 | 이벤트 처리기가 state를 바꾼다 | [[렌더링 첫걸음 03 - React 첫 만남\|03]] |
| 3 | React가 렌더하고 DOM에 커밋한다 | [[렌더링 첫걸음 04 - 렌더와 커밋\|04]] |
| 4 | `useLayoutEffect`, (경우에 따라) `useEffect` | [[렌더링 첫걸음 05 - 생명 주기와 useEffect\|05]]·[[렌더링 첫걸음 06 - Effect 심화\|06]] |
| 5 | 브라우저가 스타일 → 레이아웃 → 페인트 → 합성 | [[렌더링 첫걸음 01 - 브라우저는 화면을 어떻게 그릴까\|01]] |

한 주자라도 느리면 **결승선 도착이 늦어집니다**. 그 시간이 INP입니다.

## 2. 웹: 클릭 한 번의 타임라인

### 2.1 직접 해 보기: 실행 순서 기록

버튼을 누르면 state 두 개를 바꾸고, 처리기 안에서 마이크로태스크와 `setTimeout`도 예약하는 컴포넌트입니다.

```jsx
function App() {
  const [count, setCount] = useState(0);
  const [label, setLabel] = useState("대기");
  log(`[렌더] count=${count}, label=${label}, DOM 글자="${버튼의 현재 글자}"`);

  useLayoutEffect(() => { /* count>0이면 DOM 글자 기록 */ }, [count]);
  useEffect(() => { /* count>0이면 기록 */ }, [count]);

  function handleClick() {
    log("[이벤트 처리기] 시작");
    setCount(count + 1);
    setLabel("눌림");
    queueMicrotask(() => log("[마이크로태스크] 처리기 안에서 예약"));
    setTimeout(() => log("[setTimeout] 처리기 안에서 예약"), 0);
    log("[이벤트 처리기] 끝");
  }
  return <button onClick={handleClick}>{label} {count}</button>;
}
```

클릭했을 때 (실행 결과):

```
[이벤트 처리기] 시작
[이벤트 처리기] 끝
[렌더] count=1, label=눌림, DOM 글자="대기 0"   ← 렌더 중에는 DOM이 아직 옛 상태
[useLayoutEffect] DOM 글자="눌림 1"            ← 커밋 뒤라 새 DOM
[useEffect] count=1                            ← 클릭이 원인: 곧바로 실행
[마이크로태스크] 처리기 안에서 예약
[setTimeout] 처리기 안에서 예약
```

관찰:
- `setCount`와 `setLabel` 두 번 바꿨지만 **렌더는 한 번**입니다. 처리기가 **끝난 뒤에** 렌더가 시작됩니다. react.dev: "React processes state updates after event handlers have finished running. This is called batching." (*Queueing a Series of State Updates*)
- 렌더 중에는 DOM이 옛 글자, 레이아웃 Effect에서는 새 글자입니다 ([[렌더링 첫걸음 04 - 렌더와 커밋|레슨 04]]의 렌더 → 커밋).
- 클릭이 원인인 `useEffect`가 레이아웃 Effect **바로 뒤**, 처리기에서 예약한 마이크로태스크보다도 먼저 실행됐습니다. [[렌더링 첫걸음 06 - Effect 심화|레슨 06]] 2절의 "If your Effect is caused by an interaction (like a click), React may run your Effect before the browser paints the updated screen."과 맞는 결과입니다 (판단: jsdom에는 페인트가 없으므로 페인트 전인지는 직접 관찰하지 못함).

### 2.2 비교: 클릭이 아니라 타이머가 바꾸면

같은 갱신을 `setTimeout` 콜백에서 일으켜 봤습니다 (실행 결과):

```
[타이머 콜백] setCount 호출
[마이크로태스크] 콜백 안에서 예약
[렌더] count=1
[useLayoutEffect]
[setTimeout] 콜백 안에서 예약
[useEffect]                                    ← 다음 setTimeout보다도 뒤
```

이번에는 `useEffect`가 한참 뒤로 밀렸습니다. 상호작용이 아니면 "React will generally let the browser **paint the updated screen first before running your Effect.**" (react.dev *useEffect* Caveats)라는 설명과 맞는 순서입니다 (판단: 페인트 자체는 jsdom에서 관찰 불가).

### 2.3 한 장으로 보기

```
입력 ─┬─ (입력 지연) 메인 스레드가 다른 일 중이면 대기
      ├─ 이벤트 처리기 실행 (setState는 모아 둠)
      ├─ React 렌더: 컴포넌트 함수 호출 (DOM은 아직 그대로)
      ├─ React 커밋: 바뀐 DOM만 수정
      ├─ useLayoutEffect
      ├─ (클릭이 원인이면) useEffect가 여기서 실행될 수 있음
      ├─ 브라우저: 스타일 → 레이아웃 → 페인트 → 합성
      └─ 화면에 새 프레임 ★
                          ↑ 입력부터 ★까지 = INP가 재는 시간
```

(판단: 레슨 01–06과 위 실험을 한 줄로 이은 것)

### 2.4 INP를 세 구간으로

web.dev는 INP를 세 구간으로 나눕니다: "the input delay the time before any callback for an interaction is handled, the processing duration the time for all the callbacks to execute, and the presentation delay the time after the callbacks have been executed until the frame is presented on the user's screen." (web.dev *Interaction to Next Paint (INP)*)

| 구간 | 위 그림에서 | 느려지는 흔한 원인 | 레슨 |
|---|---|---|---|
| 입력 지연 | 입력 → 처리기 시작 | 다른 긴 작업(50 ms 넘는 작업)이 메인 스레드를 붙잡음 | 02 3절 |
| 처리 시간 | 처리기 실행 | 처리기 안의 무거운 계산 | 02 3절 |
| 표시 지연 | 처리기 끝 → 화면 | 큰 렌더, 많은 DOM 변경, 무거운 `useLayoutEffect`, 레이아웃·페인트 비용 | 04, 06 1.3절, 01 |

(구간 정의는 web.dev, 원인과 레슨 연결은 판단)

React의 렌더·커밋은 처리기가 **끝난 뒤** 실행되므로(2.1절 실험) 대부분 **표시 지연**에 들어갑니다 (판단).

## 3. React Native: 같은 클릭, 다른 길

### 3.1 타임라인

```
터치 ── UI 스레드가 받음
         │  (JS 스레드로 전달)
         ▼
      JS 스레드: 이벤트 처리기 → React 렌더 → Shadow Tree (C++)
         │        → 커밋: Yoga로 레이아웃
         ▼
      UI 스레드: 마운트 (바뀐 네이티브 뷰만) → 화면 ★
```

- 터치는 메인(UI) 스레드에서 들어와 JS 스레드로 넘어갑니다. 공식 문서는 JS 스레드가 바쁠 때 "cannot process the raw touch events sent over from the main thread"라고 설명합니다 (reactnative.dev *Performance Overview*).
- 렌더와 레이아웃은 흔한 경우 JS 스레드에서: "This is where React's render phase, as well as layout, are executed." (*Threading Model*)
- 마운트는 UI 스레드에서: "This step executes in the _host platform_ on UI thread." (*Render, Commit, and Mount*)

→ [[렌더링 첫걸음 07 - React Native는 화면을 어떻게 그릴까|레슨 07]]

### 3.2 웹과 나란히

| 단계 | 웹 | React Native |
|---|---|---|
| 입력 받기 | 브라우저 스레드가 받아 메인 스레드에 작업으로 넘김 (WBE의 교육용 브라우저 구조) | UI 스레드 → JS 스레드 |
| 이벤트 처리기 · 렌더 | 메인 스레드 | JS 스레드 |
| 레이아웃 | 브라우저 (커밋 뒤, 메인 스레드) | Yoga (커밋 단계, 주로 JS 스레드) |
| 화면 반영 | 페인트(메인) + 합성(컴포지터 스레드) | 마운트(UI 스레드) |
| 훅 규칙 | 레슨 03–06 | **같음** (+ New Architecture의 동기 `useLayoutEffect`) |
| 느림을 재는 것 | INP, 긴 작업 | JS 프레임 레이트, UI 프레임 레이트 |

(판단: 레슨 01·02·07의 공식 인용을 표로 묶음. 웹 입력 처리는 WBE p.294: 브라우저 스레드가 이벤트를 "place tasks on the main thread's TaskRunner", 메인 스레드는 "running event handlers and callbacks". 실제 브라우저와의 대응은 "the correspondence isn't exact"라고 책이 밝힘)

### 3.3 화면을 넘나들면

버튼이 **다른 화면으로 이동**시키는 경우, 웹은 보통 이전 페이지 컴포넌트를 언마운트하지만 React Navigation은 이전 화면을 **마운트된 채로** 둡니다. 화면이 보일 때만 할 일은 `useFocusEffect`로 합니다 → [[렌더링 첫걸음 08 - 앱과 화면의 생명 주기|레슨 08]]

## 4. 성능 체크리스트

### 4.1 웹

| 확인할 것 | 이유 | 근거 |
|---|---|---|
| 50 ms를 넘는 작업이 있는가 | 입력 지연·처리 시간 증가 | web.dev *Optimize long tasks* (레슨 02) |
| 큰 작업을 나눠 양보하는가 (`scheduler.yield()`, `setTimeout`) | 그 사이에 입력과 그리기가 가능 | web.dev (레슨 02 3.2절) |
| 계산 가능한 값을 Effect + state로 만들지 않았는가 | 렌더 2배 | react.dev (레슨 06 4.1절 실험) |
| 큰 목록을 입력마다 렌더 경로에서 필터링하지 않는가 | INP 악화 | Osmani p.72 |
| `useLayoutEffect`를 꼭 필요한 곳에만 썼는가 | 페인트를 붙잡음 | react.dev (레슨 06 1.3절) |
| 나중에 들어오는 콘텐츠의 자리를 잡아 두었는가 | CLS | Osmani p.69–70 (레슨 06 9.1절) |
| 애니메이션은 `transform`·`opacity`로 하는가 | 컴포지터 스레드에서 돌 수 있음 | Osmani p.92 (레슨 02 8.2절) |

### 4.2 React Native

| 확인할 것 | 이유 | 근거 (*Performance Overview*) |
|---|---|---|
| 릴리스 빌드로 측정하는가 | "JavaScript thread performance suffers greatly when running in dev mode." | 레슨 07 9.3절 |
| 배포 빌드에서 `console.log`를 없앴는가 | "can cause a big bottleneck in the JavaScript thread" | 레슨 07 9.3절 |
| `Animated`에 `useNativeDriver: true`를 쓰는가 | 그렇지 않으면 "calculates each keyframe on-demand on the JavaScript thread" | 아래 9.3절 |
| 큰 `FlatList`에 `getItemLayout`을 구현했는가 | 항목 측정을 건너뛰어 렌더가 빨라짐 | 레슨 07 9.3절 |
| 보이지 않는 화면에서 폴링·타이머가 멈추는가 | 화면은 언마운트되지 않음 | React Navigation (레슨 08) |
| 앱이 백그라운드로 가면 멈추는가 | 배터리·자원 | `AppState` (레슨 08) |

## 5. 시리즈 정리

| 레슨 | 한 줄 요약 |
|---|---|
| 01 | 브라우저는 HTML → DOM → 스타일 → 레이아웃 → 페인트 → 합성으로 화면을 만든다 |
| 02 | 1초 60프레임(16.67 ms). 작업이 끝나야 그린다. 긴 작업은 나누고 양보한다 |
| 03 | 컴포넌트는 함수, state가 바뀌면 다시 렌더. state는 스냅샷 |
| 04 | 트리거 → 렌더(계산) → 커밋(DOM) → 페인트. 바뀐 DOM만 고친다 |
| 05 | Effect는 렌더 바깥 세상과 맞추기. 설정·의존성·정리 |
| 06 | `useLayoutEffect`는 페인트 전. Strict Mode 두 번 실행. Effect가 필요 없는 경우. 경쟁 상태 |
| 07 | React Native: Render → Commit(Yoga) → Mount(UI 스레드). JS 스레드와 UI 스레드 |
| 08 | 생명 주기는 컴포넌트·화면·앱 세 겹. 화면은 언마운트되지 않는다 |
| 09 | 클릭 → 처리기 → 렌더 → 커밋 → Effect → 화면. 그 시간이 INP |

## 6. 정리

| 낱말 | 뜻 |
|---|---|
| 일괄 처리 (batching) | 처리기 안의 state 변경을 모아 처리기가 끝난 뒤 한 번에 렌더 |
| 입력 지연 | 입력부터 처리기가 시작될 때까지 |
| 처리 시간 | 처리기들이 실행되는 시간 |
| 표시 지연 | 처리기가 끝난 뒤 새 프레임이 화면에 나올 때까지 |
| JS / UI 프레임 레이트 | React Native에서 두 스레드 각각의 초당 프레임 수 |

## 7. 자주 하는 실수

| 실수 | 결과 | 바로잡기 |
|---|---|---|
| `setState` 직후 DOM이 바뀌었다고 생각하고 DOM을 읽음 | 옛 값을 읽음 | 처리기가 끝난 뒤 렌더·커밋됨 (2.1절). 커밋 뒤 DOM은 `useLayoutEffect`에서 |
| 처리기 안에서 무거운 계산을 끝까지 함 | 처리 시간 → INP 증가 | 나누고 양보 (레슨 02) |
| "INP는 이벤트 처리기 시간"이라고 생각 | 렌더·페인트 비용을 놓침 | INP는 다음 프레임이 화면에 나올 때까지 (2.4절) |
| React Native 성능을 개발 모드에서 판단 | 실제보다 훨씬 느리게 보임 | 릴리스 빌드 (4.2절) |
| JS로 계산하는 애니메이션을 무거운 렌더와 동시에 | JS 스레드가 막혀 애니메이션 멈춤 | `useNativeDriver: true` (9.3절) |

## 8. 확인 퀴즈

**Q1.** 처리기 안에서 `setA(1); setB(2); setC(3);`을 불렀습니다. 렌더는 몇 번 일어날까요?

> [!question]- 정답 보기
> 한 번입니다. React는 처리기가 끝난 뒤 모아서 처리합니다(batching). 2.1절 실험에서도 state 두 개를 바꿨지만 렌더는 한 번이었습니다.

**Q2.** INP가 나쁜데, 이벤트 처리기는 5 ms 만에 끝납니다. 어디를 의심해야 할까요?

> [!question]- 정답 보기
> 입력 지연(그 전에 실행 중이던 긴 작업)과 표시 지연(큰 렌더, 많은 DOM 변경, 무거운 `useLayoutEffect`, 레이아웃·페인트 비용)입니다. INP는 처리기 시간만이 아니라 다음 프레임이 화면에 나올 때까지를 잽니다.

**Q3.** React Native에서 버튼을 누르고 2초 걸리는 계산을 JS 스레드에서 했습니다. 그동안 (a) `ScrollView` 스크롤 (b) `useNativeDriver: true` 애니메이션 (c) 버튼 숫자 갱신은 각각 어떻게 될까요?

> [!question]- 정답 보기
> (a) 됩니다 — `ScrollView`는 UI 스레드에 있습니다. (b) 계속 움직일 수 있습니다 — 네이티브 드라이버는 JS 스레드에서 매 프레임을 계산하지 않습니다 (판단: 9.3절 인용에서). (c) 계산이 끝나야 렌더가 진행되므로 늦어집니다.

**Q4.** 클릭으로 바뀐 state에 반응하는 `useEffect`와, 타이머로 바뀐 state에 반응하는 `useEffect`의 실행 시점은 어떻게 다를까요?

> [!question]- 정답 보기
> 클릭이 원인이면 페인트 전에 실행될 수 있고(2.1절 실험에서 커밋 직후 바로 실행), 상호작용이 아니면 대개 브라우저가 먼저 그린 뒤 실행됩니다(2.2절 실험에서 한참 뒤로 밀림). 꼭 페인트 전이어야 하면 `useLayoutEffect`를 씁니다.

**Q5.** 시리즈 전체를 떠올리며, 웹과 React Native에서 **같은 것**과 **다른 것**을 하나씩 말해 보세요.

> [!question]- 정답 보기
> 같은 것: 컴포넌트·state·훅·Effect 규칙, 렌더(계산)와 커밋(반영)의 구분, "바뀐 것만 고친다"는 원리, 긴 작업이 반응을 늦춘다는 원리.
> 다른 것: 그리는 주체(브라우저 vs 네이티브 뷰), 레이아웃 엔진(브라우저 vs Yoga), 스레드 구성, 화면 생명 주기(언마운트 vs 마운트 유지), 앱 생명 주기(`AppState`).

## 9. 더 깊이 (심화)

### 9.1 왜 클릭은 다르게 다룰까

react.dev는 상호작용이 원인인 Effect를 페인트 전에 실행할 수 있는 이유로 "This ensures that the result of the Effect can be observed by the event system."을 듭니다 (*useEffect* Caveats). 또 여러 번의 클릭은 묶지 않습니다: "**React does not batch across *multiple* intentional events like clicks**--each click is handled separately." 예를 들어 첫 클릭이 폼을 비활성화했다면 두 번째 클릭이 다시 제출하지 않게 하기 위해서입니다 (*Queueing a Series of State Updates*).

2.1과 2.2절 실험의 차이(클릭은 렌더가 처리기 직후, 타이머는 렌더가 별도 작업)는 React가 갱신의 **원인**에 따라 우선순위를 다르게 매긴다는 것을 보여 줍니다 (판단: 실행 결과에서 추론. React 내부의 우선순위 구조는 [[React Fiber and Reconciliation]]).

### 9.2 React Native의 이벤트 루프

New Architecture는 HTML 표준을 따르는 이벤트 루프를 구현해 "React is able to predictably order updates and events. This allows React to interrupt a low priority update with an urgent user event" (*The New Architecture is Here*). 2.1–2.2절에서 본 "클릭은 급하게, 나머지는 나중에"가 React Native에서도 같은 원리로 동작할 기반입니다 (판단).

### 9.3 네이티브 드라이버

"The `Animated API` currently calculates each keyframe on-demand on the JavaScript thread unless you set `useNativeDriver: true`, while `LayoutAnimation` leverages Core Animation and is unaffected by JS thread and main thread frame drops." (*Performance Overview*) 웹에서 `transform`·`opacity` 애니메이션이 컴포지터 스레드에서 도는 것(레슨 02 8.2절)과 비슷한 발상입니다: **바쁜 스레드를 피해서 움직인다** (판단).
