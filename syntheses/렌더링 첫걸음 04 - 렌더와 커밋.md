# 렌더링 첫걸음 04 - 렌더와 커밋

> **이전**: [[렌더링 첫걸음 03 - React 첫 만남|03 React 첫 만남]] · **다음**: [[렌더링 첫걸음 05 - 생명 주기와 useEffect|05 생명 주기와 useEffect]] · **목록**: [[렌더링 첫걸음 00 - 로드맵|로드맵]]

## 이 레슨에서 배우는 것

1. React가 화면을 바꾸는 세 단계: **트리거 → 렌더 → 커밋**, 그리고 브라우저의 **페인트**
2. "렌더"는 **화면을 그리는 것이 아니라 컴포넌트 함수를 부르는 것**
3. 커밋은 **바뀐 부분만** DOM에 반영한다
4. state는 컴포넌트의 **위치**에 붙어 있고, `key`로 초기화할 수 있다
5. 렌더는 **순수**해야 하는 이유

> 예제는 React 19.3.1 + react-dom + jsdom에서 실행해 결과를 확인했습니다.

---

## 1. 식당 주방의 세 단계

### 비유로 이해하기: 주문 → 요리 → 서빙

react.dev는 React를 식당에 비유합니다 (*Render and Commit*).

1. **Triggering** a render (delivering the guest's order to the kitchen) — 손님 주문을 주방에 전달
2. **Rendering** the component (preparing the order in the kitchen) — 주방에서 요리
3. **Committing** to the DOM (placing the order on the table) — 완성된 요리를 테이블에 놓기

그리고 마지막에 **브라우저가 화면을 칠합니다**. react.dev: "After rendering is done and React updated the DOM, the browser will repaint the screen." 이것이 [[렌더링 첫걸음 01 - 브라우저는 화면을 어떻게 그릴까|레슨 01]]의 스타일 → 레이아웃 → 페인트 → 합성입니다.

```
트리거 ──▶ 렌더 ──▶ 커밋 ──▶ (브라우저) 페인트
"다시 그려 줘"  함수 호출   DOM 바꾸기   픽셀 칠하기
     └─── React가 하는 일 ───┘     └ 브라우저 ┘
```

---

## 2. 트리거: 언제 다시 그리나

렌더가 일어나는 이유는 두 가지뿐입니다 (*Render and Commit*):

1. "It's the component's **initial render.**" — 앱이 처음 시작할 때 (`createRoot(...).render(<App />)`)
2. "The component's (or one of its ancestors') **state has been updated.**" — [[렌더링 첫걸음 03 - React 첫 만남|레슨 03]]의 `setCount` 등

---

## 3. 렌더: 컴포넌트 함수를 부르는 것

### 3.1 "렌더"는 그리는 게 아니다

react.dev: "**"Rendering" is React calling your components.**" React 용어의 "렌더"는 **컴포넌트 함수를 호출해서 다음 화면이 어떻게 생겨야 하는지 계산하는 것**입니다. 아직 아무것도 화면에 그리지 않습니다.

> React 문서는 브라우저가 화면을 칠하는 것을 헷갈리지 않게 따로 **"painting"** 이라고 부릅니다: "Although this process is known as "browser rendering", we'll refer to it as "painting" to avoid confusion throughout the docs." 이 시리즈도 같은 구분을 씁니다. **렌더 = React가 계산**, **페인트 = 브라우저가 칠하기**.

실험으로 확인해 보면, 렌더 중에 DOM을 들여다보면 **이전 내용** 그대로입니다. 새 내용이 DOM에 들어가는 것은 커밋 뒤입니다 ([[React Component Lifecycle and Effects]] 2.2절의 실험).

### 3.2 부모가 다시 렌더되면 자식도

"This process is recursive: if the updated component returns some other component, React will render _that_ component next" (*Render and Commit*)

```jsx
function Child() {
  console.log("[render] Child");
  return <span>자식</span>;
}

function Parent() {
  const [n, setN] = useState(0);
  console.log(`[render] Parent n=${n}`);
  return (
    <div>
      <button onClick={() => setN(n + 1)}>+</button>
      <Child />
    </div>
  );
}
```

버튼을 한 번 누른 뒤의 로그 (실행 결과):

```
[render] Parent n=0
[render] Child
[render] Parent n=1
[render] Child      ← Child는 props가 그대로인데도 다시 불림
```

부모의 state만 바뀌었는데 자식 함수도 다시 불렸습니다. 이것이 React의 기본 동작입니다. react.dev는 이것이 성능 문제가 될 때를 위한 방법이 따로 있다고 하면서도 "**Don't optimize prematurely!**"라고 덧붙입니다. → [[React Hooks and Component Design Patterns]] (리렌더링 조건과 최적화)

## 4. 커밋: 바뀐 부분만 DOM에

### 4.1 공식 설명

- 첫 렌더: "React will use the `appendChild()` DOM API to put all the DOM nodes it has created on screen."
- 다시 렌더: "React will apply the minimal necessary operations (calculated while rendering!) to make the DOM match the latest rendering output."
- "**React only changes the DOM nodes if there's a difference between renders.**"

(react.dev *Render and Commit*)

### 4.2 직접 확인: 입력창의 글자가 지워지지 않는다

react.dev의 시계 예제를 따라 해 봅니다.

```jsx
function Clock({ time }) {
  return (
    <div>
      <h1>{time}</h1>
      <input />
    </div>
  );
}
```

`time`을 `"10:00:00"`으로 그린 뒤, 입력창에 글자를 써 넣고, `time`을 `"10:00:01"`로 바꿔 다시 그렸습니다 (실행 결과):

| 확인 | 결과 |
|---|---|
| `<h1>` 내용 | `10:00:01`로 바뀜 |
| `<h1>`이 같은 DOM 노드인가 | `true` (새로 만들지 않고 글자만 바꿈) |
| `<input>`이 같은 DOM 노드인가 | `true` |
| 입력창에 써 둔 글자 | 그대로 남아 있음 |

react.dev: "React only updates the content of `<h1>` with the new `time`. It sees that the `<input>` appears in the JSX in the same place as last time, so React doesn't touch the `<input>`—or its `value`!"

### 4.3 왜 중요한가: 레슨 01과 이어 보기

DOM을 바꾸면 브라우저는 스타일 → 레이아웃 → 페인트를 다시 해야 합니다 ([[렌더링 첫걸음 01 - 브라우저는 화면을 어떻게 그릴까|레슨 01]] 6절). React가 **바뀐 부분만** DOM을 건드리면 브라우저가 다시 할 일도 줄어듭니다 (판단).

## 5. state는 "위치"에 붙어 있다

### 5.1 같은 자리, 같은 컴포넌트면 state 유지

react.dev: "**React preserves a component's state for as long as it's being rendered at its position in the UI tree.** If it gets removed, or a different component gets rendered at the same position, React discards its state." (*Preserving and Resetting State*)

```jsx
function Counter({ label }) {
  const [c, setC] = useState(0);
  return <button onClick={() => setC(c + 1)}>{label}:{c}</button>;
}
```

실험 (실행 결과):

| 상황 | 화면 |
|---|---|
| `<Counter label="A" />`를 두 번 누름 | `A:2` |
| 같은 자리에 `<Counter label="B" />` (컴포넌트는 같고 props만 다름) | **`B:2`** ← state 유지 |
| 같은 자리를 잠깐 다른 컴포넌트로 바꿨다가 다시 `Counter` | **`B:0`** ← state 초기화 |

"it's the position in the UI tree--not in the JSX markup--that matters to React!" (*Preserving and Resetting State*)

### 5.2 `key`로 일부러 초기화하기

같은 자리여도 **`key`가 다르면** React는 다른 컴포넌트로 봅니다. "Specifying a `key` tells React to use the `key` itself as part of the position, instead of their order within the parent." (*Preserving and Resetting State*)

```jsx
<Counter key={person} label={person} />
```

| 상황 | 화면 (실행 결과) |
|---|---|
| `person="철수"`일 때 한 번 누름 | `철수:1` |
| `person="영희"`로 바뀜 (`key`도 바뀜) | **`영희:0`** ← 초기화 |

채팅 앱에서 상대를 바꿨을 때 입력하던 글을 지우고 싶은 경우처럼, "다른 대상이면 처음부터"가 필요할 때 씁니다 (*Preserving and Resetting State*의 채팅 예). 레슨 06에서 "Effect 대신 `key`로 초기화하기"로 다시 나옵니다.

## 6. 렌더는 순수해야 한다

렌더는 "다음 화면 계산"이므로 **순수한 계산**이어야 합니다 (*Render and Commit*):
- "**Same inputs, same output.** Given the same inputs, a component should always return the same JSX."
- "**It minds its own business.** It should not change any objects or variables that existed before rendering."

순수하지 않은 예를 Strict Mode에서 그려 봅니다.

```jsx
let guest = 0;

function Cup() {
  guest = guest + 1;            // ❌ 렌더 중에 바깥 변수를 바꿈
  return <li>손님 #{guest}</li>;
}

// <StrictMode><ul><Cup /><Cup /><Cup /></ul></StrictMode>
```

결과 (실행 결과, 개발 빌드): `손님 #2`, `손님 #4`, `손님 #6`

Strict Mode가 개발 중에 컴포넌트 함수를 **두 번** 불러서, 바깥 변수가 두 배로 늘어난 것이 드러났습니다. react.dev의 같은 예도 "Guest #2", "Guest #4", "Guest #6"이 나온다고 설명합니다 (*Keeping Components Pure*). 고친 버전은 번호를 **props로 받습니다**: `<Cup n={1} />` → `손님 #1, #2, #3` (실행 결과).

> 렌더가 순수해야 React가 렌더를 여러 번 하거나, 중간에 멈췄다 다시 하는 것이 안전해집니다 (판단: 10.1절의 Fiber 참고).

## 7. 정리

| 낱말 | 뜻 |
|---|---|
| 트리거 | 다시 그려 달라는 요청. 첫 렌더 또는 state 변경 |
| 렌더 (React) | 컴포넌트 함수를 불러 다음 화면을 계산. DOM은 아직 그대로 |
| 커밋 | 계산 결과 중 바뀐 부분만 DOM에 반영 |
| 페인트 (브라우저) | 바뀐 DOM으로 스타일·레이아웃·페인트·합성 |
| 위치 | state가 붙는 곳. 같은 자리·같은 컴포넌트면 유지 |
| `key` | 같은 자리라도 다른 대상으로 구별하게 하는 이름표. 바뀌면 state 초기화 |
| 순수한 렌더 | 같은 입력이면 같은 JSX, 바깥 값을 바꾸지 않음 |

## 8. 자주 하는 실수

| 실수 | 결과 | 바로잡기 |
|---|---|---|
| "렌더 = 화면에 그려짐"이라고 생각 | 렌더 중에 DOM을 읽고 엉뚱한 값을 얻음 | 렌더는 계산, DOM 반영은 커밋. DOM을 읽어야 하면 레슨 05–06의 Effect에서 |
| 렌더 중에 바깥 변수·DOM을 바꿈 | Strict Mode에서 값이 두 배로 바뀜 (6절) | 필요한 값은 props·state로 계산 |
| 대상이 바뀌었는데 state가 그대로 남음 (예: 사람 A의 입력값이 B 화면에 남음) | 같은 자리·같은 컴포넌트라 state 유지됨 | `key={대상.id}`로 구별 (5.2절) |
| 조건에 따라 같은 컴포넌트를 다른 자리에 그림 | 의도치 않게 state가 초기화됨 | 위치(트리 구조)를 맞추거나 `key`를 명시 |

## 9. 확인 퀴즈

**Q1.** React의 세 단계와 그 뒤 브라우저 단계를 순서대로 쓰세요.

> [!question]- 정답 보기
> 트리거 → 렌더 → 커밋 → (브라우저) 페인트

**Q2.** 다음 중 렌더가 일어나는 경우를 모두 고르세요. ① 앱이 처음 뜰 때 ② 부모 컴포넌트의 state가 바뀔 때 ③ 컴포넌트 안의 보통 변수가 바뀔 때

> [!question]- 정답 보기
> ①, ②입니다. 부모(조상)의 state가 바뀌면 그 아래 컴포넌트도 다시 렌더됩니다. 보통 변수 변경은 렌더를 일으키지 않습니다 (레슨 03).

**Q3.** 시계 예제에서 시간이 바뀔 때 입력창에 써 둔 글자가 지워지지 않는 이유는?

> [!question]- 정답 보기
> 커밋 단계에서 React는 바뀐 부분(`<h1>`의 글자)만 DOM에 반영하고, 같은 자리에 그대로 있는 `<input>`은 건드리지 않기 때문입니다.

**Q4.** `<Counter key={userId} />`에서 `userId`가 바뀌면 `Counter`의 state는 어떻게 될까요?

> [!question]- 정답 보기
> 초기화됩니다. `key`가 바뀌면 React는 다른 컴포넌트로 보고 이전 state를 버립니다.

**Q5.** 아래 컴포넌트가 순수하지 않은 이유는?
```jsx
let total = 0;
function Item({ price }) {
  total += price;
  return <li>{price}원 (누적 {total})</li>;
}
```

> [!question]- 정답 보기
> 렌더 중에 바깥 변수 `total`을 바꿉니다 ("It minds its own business" 위반). 렌더가 두 번 일어나면(Strict Mode 등) 누적값이 틀어집니다. 합계는 부모에서 배열로 계산해 props로 넘깁니다.

## 10. 더 깊이 (심화)

### 10.1 Fiber와 재조정

React가 "이전 결과와 새 결과를 비교해 바뀐 부분을 찾는 일"을 **재조정**(reconciliation)이라고 하고, 지금의 React는 **Fiber**라는 구조로 이 일을 합니다. 이 위키의 정리에 따르면 렌더 단계는 중간에 멈췄다 다시 할 수 있고, 커밋 단계는 한 번의 동기적 패스로 끝까지 실행됩니다. 자세한 내용은 [[React Fiber and Reconciliation]] 2절, [[React and React Native Internal Implementation Deep Dive]].

### 10.2 같은 "커밋"이라는 말, 다른 뜻

[[2025-Web Browser Engineering]]에도 **commit**이 나오지만, 그것은 브라우저 안에서 메인 스레드가 계산한 그리기 목록을 컴포지터(브라우저) 스레드로 넘기는 일입니다 (p.294–300). React의 커밋(DOM 반영)과는 다른 단계입니다. 순서로 보면: React 커밋(DOM 변경) → 브라우저의 스타일·레이아웃·페인트 → 브라우저 내부 commit → 래스터·합성 (판단: 두 출처를 이어 붙인 정리).

### 10.3 바뀐 만큼만 다시 하기

React가 바뀐 DOM만 건드리는 것과, 브라우저가 바뀐 레이아웃만 다시 계산하려는 것(WBE 16장: "the cost of a change should be proportional to the size of the change", p.498)은 같은 원칙입니다 (판단).

→ 전체 정리: [[React Component Lifecycle and Effects]] 1절
