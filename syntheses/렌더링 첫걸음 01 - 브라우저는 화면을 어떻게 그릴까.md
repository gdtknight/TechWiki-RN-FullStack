# 렌더링 첫걸음 01 - 브라우저는 화면을 어떻게 그릴까

> **이전**: [[렌더링 첫걸음 00 - 로드맵|로드맵]] · **다음**: [[렌더링 첫걸음 02 - 프레임과 이벤트 루프|02 프레임과 이벤트 루프]]

## 이 레슨에서 배우는 것

1. 브라우저가 HTML·CSS·JavaScript를 **화면의 픽셀**로 바꾸는 단계
2. **DOM**이 무엇이고, JavaScript로 어떻게 만지는지
3. **레이아웃**, **페인트**, **합성**이 각각 하는 일
4. 화면 그리기를 **막는 것**
5. 화면은 **한 번만 그리는 것이 아니라**, 바뀔 때마다 다시 그린다는 것

---

## 1. 브라우저는 화가가 아니라 공장이다

### 비유로 이해하기: 그림책 인쇄 공장

그림책 한 쪽을 찍어 내는 공장을 생각해 봅시다.

1. **원고 받기**: 출판사에서 글과 설계도를 받는다.
2. **설계도 읽기**: "제목이 있고, 그 아래 문단이 있고, 그 아래 그림이 있다"는 **구조**를 파악한다.
3. **꾸미기 규칙 적용**: "제목은 빨간색, 큰 글씨"라는 **스타일**을 각 부분에 붙인다.
4. **자리 잡기**: 종이 위 어디에, 얼마나 크게 놓을지 **위치와 크기**를 정한다.
5. **칠하기**: 글자와 색과 그림을 실제로 **칠한다**.
6. **겹쳐 찍기**: 여러 장의 투명 필름을 **겹쳐서** 최종 한 장을 만든다.

브라우저도 이렇게 정해진 순서대로 일합니다. 이 순서를 **렌더링 파이프라인**(rendering pipeline)이라고 부릅니다. MDN: "The Critical Rendering Path is the sequence of steps the browser goes through to convert the HTML, CSS, and JavaScript into pixels on the screen." (*Critical rendering path*)

---

## 2. 여섯 단계

[[2026-Web Performance Engineering in the Age of AI]](이하 Osmani) 5장은 Chrome을 예로 들어 여섯 단계로 정리합니다 (p.87–89).

| 단계 | 공장 비유 | 하는 일 |
|---|---|---|
| ① 내비게이션·가져오기 | 원고 받기 | 주소를 찾아 서버에 연결하고 HTML을 받는다 |
| ② HTML 파싱 → **DOM** | 설계도 읽기 | HTML 글자를 읽어 **트리**(DOM)로 만든다 |
| ③ CSS 파싱 → **스타일 계산** | 꾸미기 규칙 적용 | 어떤 CSS 규칙이 어느 요소에 적용되는지 계산한다 |
| ④ **레이아웃** | 자리 잡기 | 각 요소의 **크기와 위치**를 계산한다 |
| ⑤ **페인트** | 칠하기 | "여기에 빨간 사각형, 그다음 이 글자"처럼 **그리기 명령**을 만든다 |
| ⑥ **합성** | 겹쳐 찍기 | 여러 **레이어**를 합쳐 최종 화면 한 장을 만든다 |

Osmani는 이 흐름을 한 줄로 요약합니다: "Networking → Parsing → (blocking on CSS/JS) → Style → Layout → Paint → Composite." (p.91)

아래에서 ②–⑥을 하나씩 봅니다.

## 3. DOM: 브라우저가 읽은 설계도

### 3.1 HTML은 사실 트리다

```html
<html>
  <body>
    <h1>환영합니다</h1>
    <p>안녕하세요.</p>
  </body>
</html>
```

브라우저는 이 글자들을 읽어 **가지가 뻗은 나무 모양**으로 정리합니다.

```
html
└── body
    ├── h1  "환영합니다"
    └── p   "안녕하세요."
```

이 나무를 **DOM**(Document Object Model)이라고 부릅니다. HTML을 읽어 이 나무를 만드는 일을 **파싱**(parsing)이라고 합니다. [[2025-Web Browser Engineering]](이하 WBE)은 직접 HTML 파서를 만들면서, 이 나무가 "usually called the DOM tree"라고 설명합니다 (p.88). Osmani: "The renderer's main thread receives the bytes of HTML and begins to parse them into the DOM tree." (p.88)

> 파싱은 HTML을 다 받을 때까지 기다리지 않습니다. "Parsing is incremental: the browser parses and renders progressively rather than waiting for all of the HTML to download." (Osmani p.88)

### 3.2 직접 해 보기: 콘솔에서 DOM 만지기

아무 웹 페이지에서 콘솔을 열고 ([[JS 첫걸음 01 - 프로그램과 콘솔|JS 첫걸음 01]]) 아래를 입력해 보세요. 결과는 페이지마다 다릅니다. 아래 결과는 3.1절의 HTML 기준입니다 (jsdom으로 확인).

```js
document.body.children.length        // 2  ← body 아래 가지 개수
document.querySelector("h1").textContent   // "환영합니다"
```

`document`는 DOM 전체를 가리키는 **객체**입니다 ([[JS 첫걸음 09 - 객체|JS 첫걸음 09]]). `querySelector("h1")`은 나무에서 첫 번째 `h1` 가지를 찾아 줍니다.

DOM을 바꾸면 화면이 바뀝니다.

```js
document.querySelector("h1").textContent = "바뀐 제목";

const p = document.createElement("p");   // 새 문단 만들기
p.textContent = "새 문단";
document.body.appendChild(p);            // body 끝에 붙이기
```

JavaScript가 DOM을 바꾸면, 브라우저는 그 다음 단계들(스타일 → 레이아웃 → 페인트 → 합성)을 **다시** 실행해 화면에 반영합니다 (6절).

---

## 4. 스타일, 레이아웃, 페인트, 합성

### 4.1 스타일 계산

CSS를 읽어 만든 규칙 모음(CSSOM)과 DOM을 맞춰 보고, 요소마다 **최종 스타일**을 정합니다. Osmani: "computing the styles for each DOM node—which in this context means resolving CSS rules into actual styles for each element." (p.88)

`display: none`인 요소는 화면에 그릴 대상에서 아예 빠집니다. MDN: "If there's a `display: none;` set on an element, neither it, nor any of its descendants, are in the render tree." (*Critical rendering path*)

### 4.2 레이아웃: 자리 잡기

각 요소가 **얼마나 크고 어디에 있는지** 계산합니다. Osmani의 예: 너비가 `50%`인 `<div>`는 부모의 너비를 알아야 자기 너비를 계산할 수 있습니다 (p.88). 그래서 레이아웃은 나무 전체를 따라가며 계산합니다.

WBE: "layout is about producing a layout tree, whose nodes are layout objects, each associated with an HTML element and each with a size and a position." (p.106)

MDN은 처음 계산을 **레이아웃**, 그 뒤에 다시 계산하는 것을 **리플로우**(reflow)라고 부릅니다: "The first time the size and position of each node is determined is called *layout*. Subsequent recalculations of *layout* are called *reflows*." (*How browsers work*)

### 4.3 페인트: 칠하기

레이아웃이 끝나면 무엇을 어떤 순서로 그릴지 **그리기 명령 목록**을 만듭니다. Osmani: "Painting is often broken into drawing commands, like "draw a red rectangle here, then draw this text…"" (p.88)

### 4.4 합성: 겹쳐 찍기

브라우저는 화면을 여러 **레이어**(투명 필름)로 나눠 그리고, 마지막에 겹쳐서 한 장으로 만듭니다. 이 일을 **합성**(compositing)이라고 합니다. Osmani: "The compositor thread takes these painted layers … and composites them together into the final image that is displayed." (p.89)

왜 나눌까요? 바뀌지 않은 레이어는 **다시 칠하지 않고 재사용**할 수 있기 때문입니다. WBE는 합성을 "caching some rastered images on the GPU and reusing them during later frames"라고 설명합니다 (p.322).

## 5. 화면 그리기를 막는 것

모든 단계가 순서대로 깔끔하게 흐르는 것은 아닙니다. 어떤 것은 다음 단계를 **기다리게** 합니다 (Osmani p.89).

| 막는 것 | 무엇을 막나 | 이유 |
|---|---|---|
| `<script src="…">` (`defer`/`async` 없음) | HTML **파싱** | 스크립트가 HTML을 더 써 넣을 수도 있어서, 받아서 실행할 때까지 파서가 멈춤 (p.88) |
| `<link rel="stylesheet">` | 그 아래 내용의 **렌더링** | 스타일 없는 화면이 잠깐 보이는 것을 막으려고 |
| 메인 스레드의 큰 JavaScript 실행 | 입력 처리, 레이아웃·페인트 갱신 | 같은 스레드에서 한 번에 한 가지 일만 하므로 (레슨 02) |

Osmani의 예 (p.89–90): `<head>`에 CSS 링크와 일반 스크립트가 있으면, 브라우저는 CSS가 올 때까지 렌더링을 미루고, 스크립트를 받아 실행할 때까지 HTML 읽기를 멈춥니다. 스크립트가 크면 그만큼 첫 화면이 늦어집니다.

---

## 6. 한 번만 그리는 것이 아니다

첫 화면을 그린 뒤에도, **무언가 바뀔 때마다** 파이프라인의 일부가 다시 돕니다. Osmani: "This happens once initially, and then again and again for each frame update or user interaction that changes the page." (p.91)

| 바뀐 것 | 다시 도는 단계 | 비용 |
|---|---|---|
| 크기나 위치가 바뀜 (예: `height` 애니메이션) | 스타일 → **레이아웃** → 페인트 → 합성 | 큼 |
| 모양만 바뀜 | 스타일 → 페인트 → 합성 | 중간 |
| `transform`, `opacity` | 스타일 → **합성**만 | 작음 |

(web.dev *Rendering performance*의 세 경로와 Osmani p.91 정리. Osmani: "if you animate `height`, for example, that triggers layout every frame. Or they can be handled by the compositor: if you animate `transform` or `opacity`, those can often be done purely by the compositor on the GPU, without redoing the layout for each frame.")

**레이아웃은 비쌉니다.** 하나가 커지면 아래 요소들이 모두 밀리므로 넓은 범위를 다시 계산해야 할 수 있기 때문입니다 (판단, Osmani p.91 "Layout is usually O(n) with respect to the number of elements that need layout").

## 7. 정리

| 낱말 | 뜻 |
|---|---|
| 렌더링 파이프라인 | HTML·CSS·JS가 픽셀이 되기까지의 단계 |
| 파싱 | 글자(HTML, CSS)를 읽어 구조로 만드는 것 |
| DOM | 브라우저가 HTML을 읽어 만든 나무. JavaScript로 읽고 바꿀 수 있음 |
| 스타일 계산 | 요소마다 적용될 최종 CSS를 정하는 것 |
| 레이아웃 (리플로우) | 요소의 크기와 위치를 계산하는 것. 다시 하면 리플로우 |
| 페인트 | 그리기 명령을 만드는 것 |
| 합성 | 레이어를 겹쳐 최종 화면을 만드는 것 |
| 렌더링 차단 | 동기 `<script>`, CSS가 다음 단계를 기다리게 하는 것 |

## 8. 자주 하는 실수

| 실수 | 결과 | 바로잡기 |
|---|---|---|
| HTML이 다 읽히기 전에 실행되는 스크립트에서 아래쪽 요소를 찾음 (`document.querySelector("h2")`) | `null`이 나오고, 이어서 `.textContent = …`를 하면 `TypeError: Cannot set properties of null (setting 'textContent')` | 파서는 위에서부터 읽습니다. 스크립트를 아래에 두거나 `defer`를 씁니다 (판단: 5절의 파싱 순서) |
| "DOM을 바꾸면 그 줄에서 바로 화면이 바뀐다"고 생각 | — | DOM을 바꾸면 스타일·레이아웃·페인트를 거쳐야 화면에 보입니다. 그 시점은 레슨 02에서 봅니다 |
| 애니메이션을 `height`처럼 크기를 바꾸는 속성으로 만듦 | 매 프레임 레이아웃이 돌아 버벅일 수 있음 (Osmani p.91: "that triggers layout every frame") | 가능하면 `transform`, `opacity`로 만듭니다 (6절) |
| `<head>`에 큰 스크립트를 `defer` 없이 넣음 | 첫 화면이 늦게 나옴 | `defer`나 `async`를 붙이거나 `<body>` 끝에 둡니다 (Osmani p.89–90) |

## 9. 확인 퀴즈

**Q1.** 다음 단계를 올바른 순서로 늘어놓으세요: 페인트, 레이아웃, 합성, DOM 만들기, 스타일 계산

> [!question]- 정답 보기
> DOM 만들기 → 스타일 계산 → 레이아웃 → 페인트 → 합성

**Q2.** "이 상자는 너비 300px, 위에서 120px 아래에 있다"를 계산하는 단계는?

> [!question]- 정답 보기
> 레이아웃입니다. 크기와 위치를 계산합니다.

**Q3.** `display: none`인 요소는 레이아웃과 페인트 대상에 들어갈까요?

> [!question]- 정답 보기
> 들어가지 않습니다. MDN: "neither it, nor any of its descendants, are in the render tree."

**Q4.** 아래 두 애니메이션 중 브라우저 부담이 적은 것은? 이유는?
① 상자의 `height`를 매 프레임 바꾼다 ② 상자의 `transform`을 매 프레임 바꾼다

> [!question]- 정답 보기
> ②입니다. `transform`은 합성 단계에서 처리될 수 있어 레이아웃을 다시 하지 않습니다. `height`는 매 프레임 레이아웃을 일으킵니다 (Osmani p.91).

**Q5.** `<head>`에 `<script src="big.js"></script>`가 있습니다. 첫 화면이 늦어지는 이유를 설명해 보세요.

> [!question]- 정답 보기
> `defer`/`async`가 없는 스크립트는 HTML 파싱을 멈춥니다. 브라우저는 `big.js`를 받아 실행할 때까지 그 아래 HTML을 읽지 못하므로, 화면에 그릴 내용도 늦게 준비됩니다 (Osmani p.88–90).

**Q6. (직접 해 보기)** 아무 웹 페이지에서 콘솔을 열고, `document.querySelector("h1")`이 무엇을 돌려주는지 확인해 보세요. `h1`이 없는 페이지라면 무엇이 나올까요?

> [!question]- 정답 보기
> `h1`이 있으면 그 요소가, 없으면 `null`이 나옵니다. `null`에서 `.textContent`를 바꾸려 하면 `TypeError`가 납니다 (8절).

## 10. 더 깊이 (심화)

> 처음 읽을 때는 건너뛰어도 됩니다.

### 10.1 메인 스레드가 거의 다 한다

Chrome에서 한 페이지는 **렌더러 프로세스** 안에서 그려지고, 그 안의 **메인 스레드**가 JavaScript 실행, HTML 파싱, 스타일·레이아웃 계산, 이벤트 처리를 모두 맡습니다 (Osmani p.86). 합성과 스크롤은 **컴포지터 스레드**, 픽셀 채우기는 **래스터 스레드**가 돕습니다. 그래서 메인 스레드가 큰 스크립트로 바쁘면 "it can't simultaneously respond to user input or render updates" (p.86). → [[Web Browser Architecture (Chromium Blink)]]

### 10.2 프리로드 스캐너

HTML 파서가 스크립트 때문에 멈춰 있어도, **프리로드 스캐너**가 앞쪽 HTML을 미리 훑어 이미지·CSS·스크립트 다운로드를 먼저 시작합니다 (Osmani p.92). "CSS는 위에, 스크립트는 아래에"가 잘 통하는 이유 중 하나입니다.

### 10.3 레이어는 공짜가 아니다

`will-change: transform` 같은 방법으로 요소를 별도 레이어로 만들면 다른 요소의 레이아웃을 건드리지 않고 움직일 수 있지만, "since each layer is a surface, overusing layers can take a toll on memory" (Osmani p.92). WBE도 합성 레이어 수를 최적화해야 한다고 정리합니다 (p.351).

### 10.4 바뀐 만큼만 다시 계산하기

WBE 16장은 레이아웃 트리를 **캐시**로 보고 바뀐 부분만 다시 계산하는 방법을 구현합니다. 목표: "the cost of a change should be proportional to the size of the change, not the size of the page as a whole." (p.498) Chrome의 LayoutNG도 레이아웃 범위를 바뀐 하위 트리로 좁히려 합니다 (Osmani p.91).

→ 전체 정리: [[Browser Rendering Pipeline and Frame Lifecycle]]

|---|---|
| 단계 나누기 | Osmani: 내비게이션부터 합성까지 6단계 (p.87–89). web.dev: JavaScript·Style·Layout·Paint·Composite 5단계 (*Rendering performance*). WBE: 장난감 브라우저를 render(스타일·레이아웃·페인트) → raster → draw로 구현 (p.284). 이 레슨은 Osmani의 6단계를 따름 |
| "렌더 트리" | MDN은 DOM과 CSSOM을 합친 **렌더 트리**를 레이아웃의 입력으로 설명함 (*Critical rendering path*). Osmani는 "layout tree, which is mostly the DOM but with coordinates"라고 설명함 (p.88). 둘 다 "화면에 그릴 것만 담은, 좌표가 붙을 나무"라는 같은 생각 (판단) |
