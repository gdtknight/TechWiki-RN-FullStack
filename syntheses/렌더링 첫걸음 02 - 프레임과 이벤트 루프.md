# 렌더링 첫걸음 02 - 프레임과 이벤트 루프

## 이 레슨에서 배우는 것

1. **프레임**: 화면은 1초에 수십 장씩 새로 그려진다

## 1. 화면은 플립북이다

### 비유로 이해하기: 플립북

노트 귀퉁이에 그림을 한 장씩 조금씩 다르게 그리고 빠르게 넘기면, 그림이 움직이는 것처럼 보입니다. WBE: "An animation is a sequence of still pictures shown in quick succession that create an illusion of movement to the human eye." (p.316)

컴퓨터 화면도 똑같습니다. 화면은 **멈춘 그림 한 장**을 1초에 수십 번 바꿔 보여 줍니다. 이 그림 한 장을 **프레임**(frame)이라고 합니다. WBE는 이름의 유래를 이렇게 설명합니다: "each time you render it's one "frame"—like a drawing in a picture frame." (p.285)

### 1초에 60장

WBE: "we'd like the browser to render the page exactly as fast as the display hardware can refresh. On most computers, this is 60 times per second, or 16 ms per frame." (p.284)

1000 ms ÷ 60 ≈ **16.7 ms**. 브라우저가 새 프레임을 제때 그리려면, [[렌더링 첫걸음 01 - 브라우저는 화면을 어떻게 그릴까|레슨 01]]의 스타일 → 레이아웃 → 페인트까지 이 시간 안에 끝내야 합니다. MDN: "everything occupying the main thread, including calculating styles, along with reflow and paint, must take the browser less than 16.67ms to accomplish." (*How browsers work*)

이 시간을 **프레임 예산**이라고 부릅니다 (판단: 용어). 브라우저 자신의 일도 있으므로 web.dev는 개발자 코드를 더 짧게 잡으라고 합니다: "all of your work needs to be completed inside 10 milliseconds." (*Rendering performance*)

> 요즘은 1초에 60번보다 더 자주 새로 그리는 화면도 있습니다. WBE: "displays that refresh even more often are becoming more common." (p.285) 그럴수록 프레임 예산은 더 짧아집니다 (판단).

### 프레임을 놓치면: 버벅임 (jank)

예산을 넘기면 그 프레임은 제때 그려지지 못하고, 화면이 뚝뚝 끊겨 보입니다. 이것을 **jank**라고 합니다. MDN: "sluggishness in a user interface, usually caused by executing long tasks on the main thread, blocking rendering, or expending too much processor power on background processes." (*Jank*)

## 2. 이벤트 루프에 화면 그리기를 끼워 넣기

### 2.1 JS 첫걸음 11의 그림 다시 보기

[[JS 첫걸음 11 - 비동기 기초|JS 첫걸음 11]]에서 이벤트 루프는 "지금 하던 일이 끝나면 대기 줄에서 하나씩 꺼내 실행한다"고 배웠습니다. 브라우저에서는 여기에 **화면 그리기**가 끼어 있습니다.

Osmani: "the browser picks a task from the queue, runs it to completion, then processes all queued microtasks. Finally, it may render an update before starting the next tick with another task." (p.93)

```
 ┌──────────────┐   ┌───────────────────┐   ┌──────────────────────────┐
 │ 작업 1개      │ → │ 마이크로태스크     │ → │ (때가 되면) 화면 그리기    │ → 다음 작업 …
 │ 끝까지 실행   │   │ (Promise.then 등) │   │ 스타일→레이아웃→페인트→합성 │
 └──────────────┘   │ 전부 실행          │   └──────────────────────────┘
                    └───────────────────┘
```

### 2.2 직접 해 보기: 실행 순서 (Node.js·브라우저 콘솔 공통)

```js
console.log("1. 작업 시작");
setTimeout(() => console.log("4. setTimeout (다음 작업)"), 0);
Promise.resolve().then(() => console.log("3. 마이크로태스크"));
console.log("2. 작업 끝");
```

결과 (Node.js v24.19.0):

```
1. 작업 시작
2. 작업 끝
3. 마이크로태스크
4. setTimeout (다음 작업)
```

지금 작업이 끝나고 → 마이크로태스크가 먼저 → 그다음 작업(`setTimeout`). 화면 그리기는 브라우저에서 이 사이(3과 4 사이)에 끼어들 수 있습니다 (위 Osmani 인용).

### 2.3 작업이 끝나기 전에는 그리지 않는다

이 순서에서 중요한 결론이 나옵니다. **지금 실행 중인 작업이 끝나기 전에는 화면을 그리지 않습니다.** Osmani: "it runs to completion before the browser can do other work on that thread, like rendering or handling input." (p.93)

브라우저 콘솔에서 해 보세요 (주의: 3초 동안 탭이 멈춥니다).

```js
document.body.style.background = "yellow";
const start = Date.now();
while (Date.now() - start < 3000) {}   // 3초 동안 아무것도 안 하며 붙잡고 있기
document.body.style.background = "";
```

배경이 노랗게 바뀌는 것을 **볼 수 없을** 것입니다. 노랗게 바꾼 것도, 되돌린 것도 **같은 작업 안**에서 일어났고, 화면 그리기는 작업이 끝난 뒤에야 오기 때문입니다 (판단: 위 원리에서 추론. 이 시리즈 작성 환경에는 브라우저가 없어 직접 확인하지 못함). 그 3초 동안 클릭이나 스크롤도 반응하지 않습니다.

## 3. 긴 작업과 양보

### 3.1 긴 작업 (long task)

web.dev: "Any task that takes longer than 50 milliseconds is a long task." (*Optimize long tasks*) 긴 작업이 메인 스레드를 붙잡고 있는 동안에는 입력 처리도, 화면 그리기도 기다립니다. Osmani: "Only one JavaScript task runs at a time. If a task doesn't yield, nothing else can run." (p.123)

사용자 입장에서는 "버튼을 눌렀는데 반응이 없다"로 느껴집니다. 이것을 재는 지표가 **INP**(Interaction to Next Paint)입니다. 상호작용부터 **다음 프레임이 그려질 때까지**의 시간이고, 좋은 기준은 200 ms 이하입니다 (web.dev *Web Vitals*; Osmani p.34). → [[Web Performance Metrics and Core Web Vitals]]

### 3.2 해결: 작업을 나누고 양보하기

큰 일을 잘게 나누고, 조각 사이마다 메인 스레드에 **양보**(yield)하면, 그 사이에 브라우저가 입력을 처리하고 화면을 그릴 수 있습니다. web.dev: "When you yield to the main thread, you're giving it an opportunity to handle more important tasks" (*Optimize long tasks*).

### 비유로 이해하기: 한 줄 서기 놀이기구

놀이기구가 하나뿐인데 한 사람이 30분 동안 내리지 않으면 뒤의 모두가 기다립니다. 3분씩 타고 다시 줄 끝에 서면, 그 사이 다른 사람도 탈 수 있습니다. 양보는 "다시 줄 끝에 서기"입니다 (판단).

```js
const yieldToMain = () => new Promise((resolve) => setTimeout(resolve, 0));

async function processAll(items) {
  for (const item of items) {
    heavyWork(item);        // 조각 하나 처리
    await yieldToMain();    // 메인 스레드에 양보 → 그 사이 입력·그리기 가능
  }
}
```

[[JS 첫걸음 11 - 비동기 기초|JS 첫걸음 11]]의 `wait`와 같은 모양입니다. Node.js에서 조각마다 30 ms씩 걸리는 일을 6번 처리하며 확인해 보니, 양보하면 그 사이에 다른 작업(`setInterval` 콜백)이 끼어들었고, 양보하지 않으면 끝날 때까지 한 번도 끼어들지 못했습니다.

최신 브라우저에는 양보 전용 API도 있습니다: "`scheduler.yield()` is an API specifically designed for yielding to the main thread in the browser." (web.dev)

## 4. 애니메이션 전용 도구: `requestAnimationFrame`

### 4.1 "다음 프레임 그리기 직전에 불러 줘"

`requestAnimationFrame`(줄여서 rAF)은 함수를 **다음 화면 그리기 직전에** 실행해 달라고 예약합니다. MDN: "It requests the browser to call a user-supplied callback function before the next repaint." (*Window: requestAnimationFrame()*) WBE: "This API allows scripts to run code right before the browser runs its rendering pipeline, making the animation maximally smooth." (p.288)

- 한 번 예약하면 **한 번만** 실행됩니다. 계속 움직이려면 콜백 안에서 다시 예약합니다. MDN: "`requestAnimationFrame()` is one-shot."
- 호출 빈도는 보통 화면 주사율과 같습니다. MDN: "The frequency of calls to the callback function will generally match the display refresh rate."

### 4.2 직접 해 보기: 1초에 몇 번 불릴까 (브라우저 콘솔)

```js
let frames = 0;
const t0 = performance.now();

function tick() {
  frames++;
  if (performance.now() - t0 < 1000) {
    requestAnimationFrame(tick);   // 다음 프레임에도 불러 줘
  } else {
    console.log(`1초 동안 ${frames}번`);
  }
}
requestAnimationFrame(tick);
```

대부분의 화면에서 60 안팎이 나오고, 주사율이 더 높은 화면에서는 더 크게 나올 수 있습니다 (판단: MDN의 "generally match the display refresh rate"에서. 작성 환경에 브라우저가 없어 직접 확인하지 못함).

### 4.3 왜 `setTimeout`으로 애니메이션을 만들지 않을까

WBE: `setTimeout`으로 흉내 내면 브라우저의 그리기 박자와 맞지 않아 불필요한 렌더링이 생길 수 있고, rAF는 탭이 백그라운드일 때 그리기 일을 멈출 수 있다 (p.291). MDN: "`requestAnimationFrame()` calls are paused in most browsers when running in background tabs or hidden `<iframe>`s, in order to improve performance and battery life."

## 5. 정리

| 낱말 | 뜻 |
|---|---|
| 프레임 | 화면에 보이는 그림 한 장 |
| 60fps / 16.7 ms | 대부분의 화면이 1초에 새로 그리는 횟수 / 한 장당 시간 |
| 프레임 예산 | 한 프레임 안에 일을 끝내야 하는 시간 |
| jank | 프레임을 놓쳐 버벅이는 것 |
| 이벤트 루프 + 렌더링 | 작업 1개 → 마이크로태스크 전부 → (때가 되면) 화면 그리기 → 다음 작업 |
| 긴 작업 | 50 ms를 넘는 작업 |
| 양보 (yield) | 작업을 나눠 그 사이에 브라우저가 다른 일을 하게 하는 것 |
| INP | 상호작용부터 다음 프레임이 그려질 때까지의 시간. 200 ms 이하가 좋음 |
| `requestAnimationFrame` | 다음 화면 그리기 직전에 함수를 실행하도록 예약. 한 번에 한 번 |

| 실수 | 결과 | 바로잡기 |
|---|---|---|
| 큰 배열 처리, 큰 JSON 파싱을 한 번에 함 | 그동안 클릭·스크롤·애니메이션이 멈춤 | 잘게 나눠 양보하거나 웹 워커로 옮깁니다 (Osmani p.94, p.103) |

## 7. 확인 퀴즈

**Q1.** 1초에 60번 화면을 그린다면 한 프레임에 쓸 수 있는 시간은 약 몇 ms일까요?

> [!question]- 정답 보기
> 1000 ÷ 60 ≈ 16.7 ms입니다.

**Q2.** 아래 코드의 출력 순서는?
```js
console.log("A");
setTimeout(() => console.log("B"), 0);
Promise.resolve().then(() => console.log("C"));
console.log("D");
```

> [!question]- 정답 보기
> `A`, `D`, `C`, `B`입니다. 지금 작업(A, D)이 끝나고 → 마이크로태스크(C) → 다음 작업(B).

**Q3.** 2.3절의 코드에서 배경이 노랗게 보이지 않는 이유는?

> [!question]- 정답 보기
> 노랗게 바꾸기와 되돌리기가 같은 작업 안에서 일어났고, 브라우저는 작업이 끝난 뒤에야 화면을 그리기 때문입니다. 그릴 차례가 왔을 때는 이미 원래 색으로 돌아가 있습니다.

**Q4.** 긴 작업의 기준은 몇 ms일까요? 긴 작업이 INP를 나쁘게 만드는 이유는?

> [!question]- 정답 보기
> 50 ms입니다. INP는 상호작용부터 다음 프레임이 그려질 때까지의 시간인데, 긴 작업이 메인 스레드를 붙잡고 있으면 입력 처리와 화면 그리기가 모두 늦어집니다.

**Q5.** `requestAnimationFrame(tick)`을 한 번만 불렀는데 애니메이션이 한 번만 움직이고 멈췄습니다. 왜일까요?

> [!question]- 정답 보기
> rAF는 한 번 예약하면 한 번만 실행됩니다 ("one-shot"). 계속 움직이려면 `tick` 안에서 다시 `requestAnimationFrame(tick)`을 불러야 합니다.

## 8. 더 깊이 (심화)

### 8.1 브라우저 안의 작업 우선순위

Chrome의 메인 스레드 스케줄러는 작업 큐를 여러 개 두고, 입력 처리와 애니메이션(rAF)은 높게, `setTimeout`과 네트워크 콜백은 보통으로, idle 콜백은 낮게 다룹니다 (Osmani p.96–98). 하지만 **이미 실행 중인 작업은 끊지 못합니다**: "Chrome can't truly preempt the JavaScript: it's single-threaded and can't be interrupted except at awaits or yields." (p.98) 그래서 양보가 중요합니다. 개발자는 `scheduler.postTask(fn, { priority: 'user-blocking' | 'user-visible' | 'background' })`로 우선순위를 줄 수 있습니다 (p.98).

### 8.2 메인 스레드가 바빠도 계속 도는 애니메이션

`transform`과 `opacity` 애니메이션은 **컴포지터 스레드**에서 돌 수 있어서, 메인 스레드가 바빠도 부드럽게 유지됩니다 (Osmani p.92). WBE 12장은 메인 스레드(스크립트·스타일·레이아웃·페인트)와 브라우저 스레드(래스터·그리기·스크롤·입력)를 나누고, 메인 스레드가 그린 결과를 **commit**으로 넘기는 구조를 직접 구현합니다 (p.294–300). 실제 브라우저에서는 이 스레드를 "often called the compositor thread"라고 합니다 (p.294).

### 8.3 바뀐 게 없으면 그리지 않는다

WBE는 매 프레임 무조건 다시 그리면 CPU를 낭비하므로, "바뀌었음" 표시(**dirty bit**)가 있을 때만 렌더링하도록 구현합니다 (p.285–288). 또 렌더링 작업은 연달아 두 번 할 필요가 없다는 점을 이용해 중복 예약을 막습니다 (p.290).

### 8.4 마이크로태스크 기아

Osmani의 예 (p.93–94):

```js
function recursiveMicrotask() {
  Promise.resolve().then(() => {
    recursiveMicrotask();   // 마이크로태스크가 또 마이크로태스크를 만듦
  });
}
```

"Since each microtask queues another before the tick completes, the browser never gets a chance to render or handle user input." (p.94) ⚠️ 실행하면 탭이 멈춥니다.

→ 전체 정리: [[Browser Rendering Pipeline and Frame Lifecycle]], [[JavaScript Event Loop and Asynchronous Patterns]] 1.1절, [[Web Browser Architecture (Chromium Blink)]]

| 프레임 목표 | WBE는 실제 목표가 60fps(16 ms)라고 설명하면서도, 책의 장난감 브라우저는 단순화를 위해 30fps(33 ms)로 구현함 (p.284). 이 레슨은 60fps 기준 |
| 개발자 코드 예산 | MDN은 스타일·리플로우·페인트를 포함해 16.67 ms 이내. web.dev는 개발자 작업을 10 ms 이내로 권함 |
| 이벤트 루프 그림 | [[JS 첫걸음 11 - 비동기 기초]]는 렌더링을 뺀 단순 모형. 이 레슨은 브라우저의 렌더링 단계를 더한 모형 (Osmani p.93) |
